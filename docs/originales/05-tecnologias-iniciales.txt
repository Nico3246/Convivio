# Convivio — Tecnologías y arquitectura V1.0

## 1. Objetivo técnico

La aplicación **Convivio** se desarrollará con una arquitectura que cumpla estos requisitos:

- **Plataforma inicial: Android**
- **Coste mensual: 0 €**
- **Aplicación moderna y publicable**
- **Escalable a futuro**
- **Fácil de mantener**
- **Segura por roles**
- **Preparada para crecer sin rehacerla entera**

La solución elegida buscará un equilibrio entre:

- rapidez de desarrollo;
- bajo coste;
- buena experiencia de usuario;
- robustez técnica.

# 3. Tecnologías elegidas en detalle

## 3.1 Frontend móvil

### React Native

Será la tecnología base de la app móvil.

### Motivos

- permite desarrollar una app Android moderna;
- tiene una comunidad enorme;
- es una opción muy sólida para publicar en tiendas;
- facilita reutilización futura si algún día quieres iOS;
- encaja bien con tu experiencia previa.

---

## 3.2 Expo

Expo será la capa principal sobre React Native.

### Motivos

- simplifica mucho el desarrollo;
- facilita compilaciones y pruebas;
- integra bien notificaciones, autenticación y multimedia;
- acelera el desarrollo del MVP y de la versión final.

### Versión recomendada

- **Expo SDK 57 estable**

Se prioriza estabilidad antes que usar una beta más reciente.

---

## 3.3 TypeScript

Toda la aplicación se desarrollará en **TypeScript**.

### Motivos

- reduce errores;
- mejora el autocompletado;
- facilita mantener el proyecto;
- ayuda mucho en formularios, modelos de datos y permisos.

## 5.2 Estado local de interfaz

- estados visuales temporales;
- preferencias locales.

# 7. Base de datos

## PostgreSQL en Supabase

Convivio usará una base de datos relacional.

### Motivos

La app tiene mucha información conectada entre sí:

- usuarios;
- roles;
- normas;
- versiones de normas;
- faltas;
- comentarios;
- quejas;
- excepciones;
- tareas;
- turnos;
- inventarios;
- listas;
- compras;
- deudas;
- pagos;
- auditoría.

Todo esto encaja mejor en SQL que en bases de datos tipo documento.

---

# 8. Autenticación

## Supabase Auth

La autenticación se hará mediante:

- **inicio de sesión con Google**

### Motivos

- elimina formularios de contraseña;
- simplifica la experiencia;
- es cómodo para los 3 usuarios;
- reduce carga de mantenimiento.

### Comportamiento

- solo podrán entrar correos autorizados;
- no habrá registro libre;
- el rol se asignará desde la base de datos.

---

# 9. Roles y seguridad

Convivio manejará tres roles:

- **ADMIN**
- **RESIDENT**
- **CONTROLLER**

## 9.1 Control visual en la app

La interfaz mostrará u ocultará opciones según el rol.

## 9.2 Protección real en backend

La seguridad no dependerá solo del frontend.

Se aplicará protección a nivel de base de datos mediante:

- **Row Level Security (RLS)**

### Objetivo

Aunque alguien intentara manipular la aplicación, el servidor seguirá impidiendo acciones no permitidas.

---

# 10. Permisos por rol

## ADMIN

Podrá:

- gestionar usuarios;
- crear normas;
- proponer cambios de normas;
- crear tareas;
- crear turnos;
- configurar la aplicación;
- consultar auditoría.

## RESIDENT

Podrá:

- registrar faltas;
- registrar quejas;
- comentar faltas;
- consultar normas;
- gestionar tareas;
- gestionar inventario;
- registrar gastos;
- consultar y pagar deudas;
- solicitar excepciones.

## CONTROLLER

Podrá:

- consultar faltas;
- consultar quejas;
- consultar pruebas;
- mantener o invalidar faltas;
- aprobar o rechazar excepciones;
- aprobar modificaciones de normas existentes.

No podrá acceder a:

- inventario;
- listas de compra;
- gastos;
- deudas;
- apartados económicos.

Se utilizarán para la lógica que no debe vivir solo en el frontend.

### Ejemplos

- permite automatizaciones sin servidor propio.

### Uso principal

### Otros usos futuros

- limpieza de datos temporales;
- recordatorios;
- tareas de mantenimiento.

### Flujo previsto

Edge Function

# 18. Por qué no se usará un backend propio tradicional

Aunque sería posible utilizar tecnologías como:

- FastAPI;
- Node.js + Express;
- Django;
- Spring Boot;

para Convivio **no es la mejor opción en V1**.

## Razones

Montar un backend propio implicaría gestionar por separado:

- hosting;
- API;
- autenticación;
- base de datos;
- almacenamiento;
- tareas programadas;
- despliegue;
- seguridad.

Eso añade complejidad innecesaria para una app de 3 usuarios con coste 0 €.

Supabase permite resolver todo esto en una sola plataforma, manteniendo buena calidad técnica.

---

# 19. Por qué no se usará Firebase como solución principal

Firebase sería viable, pero no es la opción preferida para Convivio.

## Motivos

La app tiene mucha estructura relacional:

- faltas ligadas a normas;
- normas con versiones;
- compras que generan deudas;
- deudas con pagos parciales;
- tareas con turnos;
- historial y auditoría.

Este tipo de dominio encaja mejor en PostgreSQL que en Firestore.

Por eso se elige:

- **Supabase + PostgreSQL**
en lugar de
- **Firebase + Firestore**

---

# 20. Principios de arquitectura

La arquitectura de Convivio seguirá estos principios.

## 20.1 Separación por capas

- presentación;
- lógica de cliente;
- acceso a datos;
- lógica de backend;
- persistencia.

## 20.2 Modularidad

Cada área del sistema estará separada por dominios funcionales.

## 20.3 Seguridad real

Los permisos se comprobarán también en backend.

## 20.4 Escalabilidad

Aunque hoy sean solo 3 usuarios, el código no se diseñará como un proyecto “parcheado”.

## 20.5 Mantenibilidad

Se priorizará una estructura limpia, legible y fácil de ampliar.

# 24. Tratamiento de faltas

Cuando el controlador invalide una falta, no se hará un borrado físico.

## En lugar de eliminar definitivamente:

se cambiará su estado.

### Estados sugeridos

- `REGISTERED`
- `CONFIRMED`
- `DISMISSED`

## Ventajas

- mantiene historial;
- mejora la auditoría;
- evita pérdida real de datos;
- permite reconstruir eventos si hiciera falta.
