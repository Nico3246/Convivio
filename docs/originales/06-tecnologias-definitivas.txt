# Convivio — Informe definitivo de tecnologías y arquitectura V1.0

## 1. Objetivo técnico

Convivio se desarrollará desde el principio como una aplicación:

- sólida;
- segura;
- mantenible;
- modular;
- correctamente tipada;
- preparada para crecer;
- Android en su primera versión;
- con coste mensual objetivo de 0 €;
- preparada para una posible publicación futura.

Aunque actualmente será utilizada únicamente por tres personas, **no se desarrollará como un prototipo desechable**.

La V1 utilizará prácticas y una estructura propias de una aplicación de producción.

---

# 2. Decisión principal sobre lenguajes

Convivio utilizará principalmente dos tecnologías de programación:

## TypeScript

Será el lenguaje principal de programación.

Se utilizará para:

- aplicación Android;
- interfaz;
- lógica del cliente;
- servicios;
- modelos;
- validaciones;
- conexión con Supabase;
- Edge Functions;
- notificaciones;
- automatizaciones de servidor.

## SQL / PostgreSQL

Se utilizará para:

- estructura de datos;
- relaciones;
- restricciones;
- consultas;
- seguridad RLS;
- operaciones transaccionales;
- determinadas funciones de base de datos.

También podrá utilizarse:

## PL/pgSQL

Exclusivamente cuando resulte útil crear funciones internas de PostgreSQL.

---

# 3. Lenguajes que NO utilizaremos inicialmente

Convivio V1 no necesitará:

- Java.
- Kotlin.
- Python.
- C++.
- Spring Boot.
- FastAPI.
- Express.

Esto no significa que sean malas tecnologías.

Simplemente introducirlas en Convivio supondría añadir otra capa de servidor o más lenguajes sin aportar una ventaja suficiente.

La arquitectura queda deliberadamente reducida a:

```text
TypeScript
    +
SQL / PostgreSQL
```

---

# 4. Filosofía respecto a TypeScript

Aunque inicialmente no exista experiencia previa con TypeScript, no se utilizará como “JavaScript con algunos tipos”.

Se utilizará de forma estricta.

## Regla

El proyecto tendrá:

```text
strict = true
```

desde el primer commit.

Se evitará:

```text
any
```

salvo situaciones muy excepcionales y justificadas.

---

# 5. Ventaja para alguien procedente de Java/C++

Conceptos como:

- tipos;
- interfaces;
- enumeraciones;
- clases;
- genéricos;
- encapsulación;
- separación por módulos;
- tipado de parámetros;
- tipado de retornos;

resultarán familiares.

Ejemplo:

```text
type UserRole =
  | "ADMIN"
  | "RESIDENT"
  | "CONTROLLER";

interface User {
  id: string;
  name: string;
  email: string;
  role: UserRole;

```

El aprendizaje principal estará relacionado con:

- JavaScript moderno;
- programación asíncrona;
- React;
- React Native;
- ecosistema Expo.

# 10. Backend

No existirá inicialmente un servidor tradicional independiente.

No montaremos:

```text

      ↓
FastAPI / Spring
      ↓
PostgreSQL
```

```text
React Native
      ↓
Supabase
      ↓
PostgreSQL
```

Cuando sea necesaria lógica de servidor:

```text
React Native
      ↓
Supabase Edge Function
      ↓
PostgreSQL
```

# 11. Supabase

Supabase proporcionará:

- PostgreSQL;
- autenticación;
- almacenamiento;
- Row Level Security;
- funciones serverless;
- tareas programadas;
- API de datos;
- gestión de sesiones.

Esto elimina la necesidad de mantener varios servicios independientes.

---

# 12. Base de datos

La base de datos será:

# PostgreSQL

Esta elección es especialmente adecuada para Convivio por la gran cantidad de relaciones existentes.

Ejemplos:

```text
Usuario
   ↓
Falta
   ↓
Norma
   ↓
Versión de norma
```

o:

```text
Compra
   ↓
Participantes
   ↓
Deudas
   ↓
Pagos
```

---

# 13. PostgreSQL como parte de la robustez

La integridad no dependerá únicamente de TypeScript.

La base de datos impondrá reglas mediante:

- `PRIMARY KEY`;
- `FOREIGN KEY`;
- `NOT NULL`;
- `UNIQUE`;
- `CHECK`;
- tipos correctos;
- transacciones;
- índices.

Ejemplo conceptual:

```text
importe_deuda >= 0
```

no será simplemente una comprobación visual.

La propia base de datos impedirá valores inválidos.

# 14. División de responsabilidades

La lógica no se colocará arbitrariamente.

## Aplicación TypeScript

Responsable de:

- interfaz;
- interacción;
- navegación;
- formularios;
- validación inmediata;
- presentación de datos.

## PostgreSQL

Responsable de:

- integridad;
- relaciones;
- seguridad;
- restricciones;
- consultas;
- operaciones transaccionales.

## Edge Functions TypeScript

Responsables de:

- automatizaciones;
- coordinación de procesos;
- notificaciones;
- operaciones privilegiadas;
- integraciones externas.

---

# 15. Regla importante

Una norma crítica del negocio nunca dependerá exclusivamente de la interfaz.

Por ejemplo:

El controlador puede eliminar/inactivar una falta.

No bastará con ocultar el botón al residente.

El backend comprobará que:

```text
role == CONTROLLER
```

antes de permitir la operación.

---

# 16. Row Level Security

Supabase RLS será una parte fundamental del sistema.

Habrá políticas para:

- ADMIN;
- RESIDENT;
- CONTROLLER.

Ejemplo conceptual:

```text
RESIDENT
    ↓
puede insertar falta

CONTROLLER
    ↓
puede confirmar/inactivar falta

RESIDENT
    ↓
NO puede inactivar falta
```

Estas restricciones existirán en PostgreSQL.

# 22. Edge Functions

Las funciones de servidor se desarrollarán en:

**TypeScript**

sobre el runtime de Supabase compatible con Deno.

Casos previstos:

```text
generate-weekly-report
send-push-notification
process-visit-exception
process-rule-change
administrative-operation
```

No deberán convertirse en un backend monolítico.

Cada función tendrá una responsabilidad bien definida.

---

# 23. Lógica que NO debe ir innecesariamente en Edge Functions

No utilizaremos Edge Functions para cada operación CRUD.

Por ejemplo, consultar una lista de productos podrá realizarse directamente mediante Supabase y RLS.

Usaremos Edge Functions cuando aporten valor real:

- acción privilegiada;
- proceso complejo;
- automatización;
- varias operaciones coordinadas;
- servicio externo;
- lógica que no debe ejecutarse en el dispositivo.

---

# 24. Funciones PostgreSQL

Determinadas operaciones podrán implementarse directamente en PostgreSQL cuando necesiten:

- transacciones;
- varias tablas;
- cálculos próximos a los datos;
- consistencia fuerte.

Ejemplos potenciales:

- cálculo de balances;
- simplificación de deudas;
- estadísticas;
- operaciones transaccionales.

---

Aunque actualmente exista un solo piso, añadiremos desde el diseño:

```text

```

a las entidades que corresponda.

Eso permitirá que en el futuro Convivio pueda admitir:

```text
Piso 1
Piso 2
Piso 3
...
```

sin tener que rediseñar completamente la base de datos.

En la V1 esta funcionalidad no se expondrá al usuario.

# 57. Tratamiento de eliminaciones

Para información sensible no utilizaremos borrado físico siempre que sea importante conservar trazabilidad.

Ejemplo:

Una falta invalidada:

```text
status = DISMISSED
```

y se almacenará:

```text
dismissed_by
dismissed_at
dismiss_reason
```

No desaparecerá silenciosamente de la base de datos.

# 59. Transacciones

Las operaciones económicas críticas deberán ser atómicas.

Ejemplo:

```text
Registrar compra
      ↓
Crear gasto
      ↓
Crear participantes
      ↓
Generar deuda
```

O se realizan todas correctamente:

```text
COMMIT
```

o ninguna:

```text
ROLLBACK
```

Nunca debemos terminar con una compra guardada pero una deuda sin crear por un error intermedio.

---

# 60. Robustez de las deudas

El saldo mostrado será un dato derivado.

No confiaremos únicamente en guardar:

```text
saldo = 20
```

sin conocer su origen.

Conservaremos los movimientos:

- gastos;
- deudas;
- pagos.

El balance podrá reconstruirse.

---

# 61. Observabilidad y errores

La aplicación tendrá un sistema centralizado para:

- errores;
- logs de desarrollo;
- errores de red;
- errores inesperados.

No utilizaremos:

```text
try/catch
```

aislados por toda la aplicación sin estrategia común.

---

# 62. Manejo de errores de usuario

Los mensajes serán comprensibles.

Evitar:

```text
PostgrestError PGRST116
```

Mostrar:

```text
No se ha podido registrar la falta.
Comprueba tu conexión e inténtalo de nuevo.
```

Los detalles técnicos quedarán para logs.

---

# 63. Sin conexión

Convivio requiere conexión a Internet.

Sin embargo:

- la aplicación no deberá cerrarse;
- mostrará el estado de conexión;
- evitará enviar operaciones imposibles;
- conservará caché visual cuando sea razonable.

---

Las versiones importantes de:

- Expo;
- React Native;

- librerías;

no se actualizarán automáticamente sin revisión.

```text
actualización

branch
    ↓
typecheck

lint
    ↓
tests
    ↓
pruebas Android
    ↓
merge
```

# 65. Dependencias

Evitaremos instalar librerías para problemas pequeños que podamos resolver fácilmente.

Cada dependencia aumenta:

- mantenimiento;
- vulnerabilidades potenciales;
- riesgo de incompatibilidad.

Usaremos dependencias consolidadas y necesarias.

# 73. Principio técnico fundamental de Convivio

La aplicación no dependerá de que el frontend “se comporte correctamente”.

Las reglas importantes estarán protegidas también en backend y base de datos.

La arquitectura seguirá este principio:

**La interfaz facilita las acciones.**

**TypeScript garantiza coherencia.**

**El backend autoriza.**

**PostgreSQL protege los datos.**

**Los tests verifican el comportamiento.**

**Git conserva la evolución.**

Ese será el fundamento técnico de Convivio V1.0.
