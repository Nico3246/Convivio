# Arquitectura de pantallas y wireframes — V1.0

## 1. Enfoque general de interfaz

La aplicación deberá ser rápida de usar y evitar menús excesivamente profundos.

La navegación principal de los residentes tendrá cinco secciones:

**Inicio · Convivencia · Casa · Compra · Dinero**

El administrador tendrá además acceso a:

**Administración**

Este acceso no aparecerá como una sexta pestaña inferior, para no sobrecargar la navegación. Estará dentro del menú de perfil.

---

# 2. Navegación inferior

Barra inferior permanente:

🏠 **Inicio**

⚖️ **Convivencia**

🧹 **Casa**

🛒 **Compra**

💶 **Dinero**

La sección activa deberá quedar claramente resaltada.

---

# 3. Cabecera global

En la parte superior aparecerá:

**Nombre de la pantalla**

y a la derecha:

🔔 Notificaciones

👤 Perfil

Ejemplo:

**Inicio                           🔔 👤**

# 42. Notificaciones

La aplicación tendrá inicialmente pocas notificaciones.

Principalmente:

### Informe semanal

**Resumen semanal disponible**

### Excepción

Para las personas que deban aprobarla:

**Nueva solicitud de excepción**

### Resultado de excepción

**Tu solicitud ha sido aprobada**

o

**Tu solicitud ha sido rechazada**

---

# 43. Lo que NO generará notificación

No se notificará inmediatamente:

- Nueva falta.
- Nueva queja.
- Nuevo comentario en una falta.

Esto respeta el funcionamiento acordado y evita conflictos instantáneos innecesarios.

---

# 44. Jerarquía visual

La aplicación utilizará tres niveles visuales.

## Nivel 1

Información inmediata.

Ejemplo:

**Hoy tienes que tirar la basura.**

## Nivel 2

Información resumida.

Ejemplo:

**Debes 14,50 €.**

## Nivel 3

Históricos y detalles.

Ejemplo:

Listado completo de gastos.

Esto permitirá que Inicio sea sencillo aunque la aplicación tenga muchas funciones.

---

# 45. Diseño de tarjetas

Los elementos principales se mostrarán mediante tarjetas.

Ejemplo:

```text
┌───────────────────────────────┐
│ 🧹 LIMPIEZA                   │
│                               │
│ Limpiar baño                  │
│ Hoy                           │
│                               │
│ [ Marcar realizada ]          │
└───────────────────────────────┘
```

Las tarjetas deberán tener:

- Bordes redondeados.
- Espaciado amplio.
- Iconografía sencilla.
- Poco texto.
- Acción principal claramente visible.

---

# 46. Botón flotante

En determinadas secciones se utilizará un botón:

**+**

Por ejemplo:

Faltas → nueva falta.

Quejas → nueva queja.

Inventario → nuevo producto.

Listas → nuevo elemento.

Gastos → nuevo gasto.

---

# 47. Diseño para modo oscuro

La estructura será idéntica.

Solo cambiarán:

- Fondo.
- Superficies.
- Texto.
- Bordes.
- Contraste.

La aplicación respetará inicialmente la configuración del dispositivo.

El usuario podrá cambiarla manualmente desde Perfil.

---

# 48. Flujo principal del usuario

Al abrir la aplicación:

```text
LOGIN GOOGLE
      ↓
    INICIO
      ↓
¿Qué necesito hacer ahora?
      ↓
 ┌────┼─────┬─────┐
 ↓    ↓     ↓     ↓
Casa Falta Compra Dinero
```

La aplicación debe responder principalmente a una pregunta:

**“¿Qué tengo que hacer o saber ahora?”**

---

# 49. Principio de diseño del módulo de convivencia

Registrar una falta debe ser fácil.

Pero consultar las normas debe ser todavía más fácil.

La intención no es incentivar registrar incumplimientos, sino que las reglas sean claras y puedan comprobarse rápidamente.

# 53. MVP

Para tener una primera versión utilizable lo antes posible, el MVP podrá contener:

- Inicio de sesión con Google.
- Los tres usuarios.
- Roles.
- Normas.
- Faltas.
- Fotografías.
- Comentarios.
- Quejas.
- Controlador.
- Informe semanal.
- Notificaciones.
- Excepciones de visitas.

Después se añadirán:

- Tareas.
- Duchas.
- Limpieza.
- Compra.
- Inventarios.
- Gastos.
- Deudas.

La arquitectura estará preparada desde el principio para todos los módulos.
