# Casos de uso y flujos funcionales — V1.0

## 1. Estructura general de navegación

La aplicación tendrá una interfaz diferente según el tipo de usuario.

### 1.1 Residente administrador

Navegación principal:

**Inicio · Convivencia · Casa · Compra · Dinero · Administración**

### 1.2 Residente estándar

Navegación principal:

**Inicio · Convivencia · Casa · Compra · Dinero**

### 1.3 Controlador

Interfaz simplificada:

**Resumen · Faltas · Quejas · Excepciones**

---

# 2. Pantalla Inicio

La pantalla Inicio será diferente para residentes y controlador.

## 2.1 Inicio del residente

El objetivo será mostrar únicamente información útil del día.

### Bloque “Hoy”

Mostrará:

- Próxima ducha.
- Tareas asignadas hoy.
- Turno de basura.
- Avisos importantes.
- Excepciones de visitas pendientes.

### Bloque “Casa”

Mostrará, por ejemplo:

**Hoy limpia el baño: Usuario A**

**Basura: Usuario B**

**Ducha: 20:30–20:50**

### Bloque “Compra”

Mostrará:

- Productos compartidos pendientes.
- Productos comunes agotándose.
- Acceso rápido a la lista personal.

### Bloque “Dinero”

Mostrará únicamente el balance neto.

Ejemplo:

**Debes 14,50 €**

o

**Te deben 8,20 €**

### Acciones rápidas

Existirán dos botones destacados:

**+ Añadir falta**

**+ Añadir queja**

# 4. CU-01 — Consultar normas

## Actor

Todos los usuarios.

## Flujo

1. Usuario entra en **Convivencia > Normas**.
2. La aplicación muestra las categorías:
   - Horarios y silencio.
   - Visitas.
   - Espacios comunes.
3. El usuario selecciona una categoría.
4. Se muestran las normas vigentes.
5. Al seleccionar una norma puede consultar:
   - Título.
   - Descripción.
   - Horarios.
   - Fecha de entrada en vigor.
   - Última modificación.

Los residentes no podrán modificar las normas desde esta pantalla.

---

# 5. CU-02 — Crear una norma

## Actor

Administrador.

## Flujo

1. Administrador entra en:
   **Administración > Normas**.
2. Pulsa:
   **Nueva norma**.
3. Introduce:
   - Título.
   - Categoría.
   - Descripción.
   - Fecha de entrada en vigor.
4. Confirma.
5. La norma queda activa.
6. El sistema registra la creación en auditoría.

---

# 6. CU-03 — Modificar una norma existente

## Actor principal

Administrador.

## Actor secundario

Controlador.

## Flujo

1. Administrador abre una norma.
2. Pulsa:
   **Proponer modificación**.
3. Realiza los cambios.
4. Introduce opcionalmente el motivo.
5. Envía la propuesta.
6. La norma actual continúa vigente.
7. El controlador visualiza:
   **Cambio de norma pendiente**.
8. Puede consultar:
   - Norma actual.
   - Nueva propuesta.
   - Diferencias.
9. El controlador pulsa:
   **Aprobar**
   o
   **Rechazar**.

### Si aprueba

Se crea una nueva versión.

La nueva versión pasa a ser la vigente.

### Si rechaza

La norma anterior permanece sin cambios.

Todo queda registrado en auditoría.

---

# 7. CU-04 — Registrar una falta

## Actor

Cualquiera de los dos residentes.

## Flujo principal

1. Usuario pulsa:
   **+ Añadir falta**.
2. Selecciona:
   **Quién ha incumplido**.
3. Selecciona:
   **Norma incumplida**.
4. La aplicación introduce automáticamente:
   - Fecha.
   - Hora.
5. Usuario escribe una descripción.
6. Opcionalmente añade una fotografía.
7. Puede revisar todos los datos.
8. Pulsa:
   **Registrar falta**.
9. Aparece confirmación:
   **Falta registrada correctamente**.
10. La falta entra en el historial.

No se envía ninguna notificación inmediata.

---

# 8. Formulario de falta

Campos:

**Persona responsable**

Obligatorio.

**Norma incumplida**

Obligatorio.

**Fecha**

Automática pero editable.

**Hora**

Automática pero editable.

**Descripción**

Obligatoria.

**Fotografía**

Opcional.

La fotografía podrá:

- Tomarse con cámara.
- Seleccionarse de galería.

Antes de subirla será comprimida.

---

# 9. Estados de una falta

Una falta podrá encontrarse en:

**Registrada**

Aún no revisada por el controlador.

**Mantenida**

El controlador considera que debe permanecer.

**Eliminada por el controlador**

No aparecerá como falta válida en estadísticas, aunque el evento de eliminación permanecerá en auditoría.

## Flujo

# 12. CU-07 — Revisar una falta

## Actor

Controlador.

## Flujo

1. Controlador abre una falta.
2. Puede consultar:
   - Norma.
   - Persona.
   - Autor de la falta.
   - Descripción.
   - Fecha y hora.
   - Fotografía.
   - Comentarios.
3. Decide entre:

**Mantener falta**

o

**Eliminar falta**.

### Si pulsa “Mantener”

La falta pasa a estado:

**Mantenida**.

### Si pulsa “Eliminar”

Se solicitará confirmación.

Opcionalmente podrá indicar un motivo.

La falta se retirará de las estadísticas.

La acción quedará registrada.

# 54. Criterio general de diseño

La aplicación deberá priorizar tres cosas:

**Rapidez**

Registrar una falta, una queja, una tarea o un gasto deberá requerir pocos pasos.

**Claridad**

Siempre deberá estar claro:

- Qué corresponde hacer.
- A quién.
- Cuándo.
- Qué normas están vigentes.

**Trazabilidad**

Las decisiones relacionadas con convivencia deberán quedar registradas para evitar discusiones posteriores sobre:

- Qué ocurrió.
- Cuándo ocurrió.
- Qué norma estaba vigente.
- Quién realizó una acción.
- Qué decidió el controlador.

---

# 55. Flujo conceptual de toda la aplicación

La aplicación puede entenderse mediante cinco ciclos:

### CONVIVENCIA

Norma → Incumplimiento → Falta → Informe → Controlador → Histórico.

### PROBLEMAS

Problema → Queja → Informe → posible nueva norma.

### CASA

Tarea → Responsable → Realización → Histórico → siguiente turno.

### COMPRA

Necesidad → Lista → Compra → Inventario.

### DINERO

Compra → Gasto → Reparto → Deuda → Pago → Liquidación.
